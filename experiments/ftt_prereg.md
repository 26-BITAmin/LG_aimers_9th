# FT-Transformer 헤드 분할 — 사전 등록 (2026-08-30)

> **개인 탐색 실험이다.** MODEL.md §7 번호를 쓰지 않는다 (다른 세션과 충돌).
> 채택 후보로 승격되면 그때 §7 번호를 붙인다.
>
> base: `src/foldcache.py` fold 하네스 (배포 피처 설정 + soft label). 챔피언 층 아님.
> 코드: `src/ftt.py` · `src/ftt_groups.py`

## 무엇을 재나

헤드마다 key/value 를 피처 그룹으로 제한한 FT-Transformer. 팔 6개:

| 팔 | 마스크 | 헤드당 key |
| --- | --- | --- |
| `full` | 없음 (표준 MHA, 헤드 16) | 79 |
| `sem8` | 의미 8그룹 × 2 | 5~20 |
| `sem8ov` | 같은 8그룹 + 축 걸침 중복 | 9~22 |
| `subj3` | 투수6 · 타자5 · 상황5 | 14 / 28 / 41 |
| `shuf@sem8` · `shuf@subj3` | **위약** (크기 분포 동일, 소속 무작위) | 동일 |

전 팔 파라미터 수 동일 (마스크는 학습 안 되는 buffer). 헤드 수 16 고정.
전역 헤드 0개 — 사용자 결정, 완전 분할.

## 판정 조건 (결과 보기 전에 못 박는다)

1. **① scheme > full** — 분할이 일한다
2. **② scheme > shuf@scheme** — 그룹 **구성**이 일한다. ①만이면 그냥 마스킹 효과다
3. 둘 다 fold 2023 · 2024 에서 **부호 일치**
4. 시드폭(2시드 sd)보다 작은 차이는 안 읽는다

⚠️ 이미 스모크(60k · 2에폭)에서 **위약이 진짜를 이겼다** (462.9 vs 419.4).
   위약 팔이 없었다면 `group > full` (+67.8) 만 보고 "내 그룹이 통했다" 고 잘못 읽었다.

## 정정 1 — `id_rank` 를 낡은 config 값에서 가져왔다 (사용자 지적, 2026-08-30)

예측 #1 의 근거로 든 *"§7.27 배포 ID 임베딩 최적 = 4"* 는 **틀렸다.**
챔피언 zip 실물(`hj05_r047f330.zip` → `mlp_emb4_*.npz`):

```
pitcher_id (793, 8)   batter_id (831, 4)   나머지 4
```

`emb_dim["pitcher_id"]` 4→8 은 **LB +7.44** 였다 (§7.197). `config.MLP_VARIANTS` 에
아직 4 로 남아 있는 것은 낡은 값이고, §7.211 이 *"config 에서 파생된 모든 fold
하네스가 조용히 챔피언이 아닌 모델을 잰다"* 고 이미 경고해뒀다.
→ `DEFAULT["id_rank"]` 를 챔피언 실물 값으로 고쳤다. [[audit-inherited-constants-not-just-registered-gates]]

### 그래서 "용량 법칙" 을 다시 쓴다

내가 *"파라미터를 늘리면 진다"* 로 뭉뚱그린 것이 문제였다. 기록은 **무엇에** 파라미터를
주느냐로 갈린다:

| 변경 | 무엇에 용량을 주나 | 결과 |
| --- | --- | --- |
| §7.25 wide256 | 공유 몸통의 폭 | ❌ |
| §7.26 PLE | 수치 입력 차원 73→381 | ❌ |
| §7.197 `pitcher_id` 4→8 | **엔티티 테이블의 병목** | ✅ **LB +7.44** |

793명을 4차원에 밀어 넣는 것은 진짜 손실이었다. 반면 이미 인코딩된 입력 위에
공유 함수의 용량을 더하는 것은 노이즈만 적합했다.

**이 파이프라인은 양쪽에 다 걸쳐 있다:**
- 엔티티 테이블 세분화 → 이긴 가족 (지금 챔피언 dim 으로 맞춰놨다)
- 수치 71개를 71×64 토큰으로 펴는 것 → **PLE 와 같은 방향이고 12배 더 극단적이다**

→ 예측 #1 은 그대로 두되(사후 수정 금지), 그 **근거의 절반은 무효**다. 실제로 봐야 할
   위험은 "파라미터가 는다" 가 아니라 **"수치 표현 팽창이 §7.26 처럼 죽느냐"** 다.

### 부수 효과 — fold2023 을 어떻게 읽을지가 바뀐다

[[folds-can-be-biased-against-a-change-family]] 는 정확히 이 4→8 변경의 기록이다:
f2023 이 −5 로 약하게 읽은 것이 LB +7.44 였고, **그 fold 는 표현 세분화에만 짜다.**
이 파이프라인이 같은 가족이므로 **fold2023 이 음수여도 자동 기각하지 않는다** —
부호 불일치를 결과로 기록하되, 그 fold 의 알려진 편향을 같이 적는다.

## 정정 2 — 앵커를 낮게 잡았다 (2026-08-30)

처음에 앵커로 쓴 `emb4` 1멤버 1시드(724.1)는 **배포 MLP 슬롯이 아니다.** 슬롯은
`emb4` 5시드 + `noid` 3시드를 `.875/.125` 로 섞은 8멤버다 (§7.120, 그 가중 자체가 LB +1.85).

```
fold2024  emb4 5시드 단독 724.1 764.1 732.0 730.1 702.8   sd 22.0  → 시드평균 804.6
          noid 3시드 단독 779.7 746.1 767.4               sd 17.0  → 시드평균 796.4
          ▶ 배포 MLP 슬롯 = 808.9
fold2023  emb4 5시드 단독 580.0 561.3 626.7 558.5 560.3   sd 28.9  → 시드평균 626.0
          ▶ 배포 MLP 슬롯 = 629.0
```

내가 앵커로 쓴 724.1 은 seed 42 한 번의 뽑기였고 5개 중 아래쪽이었다.
**시드 평균만으로 +74** 가 오른다. → `full@4ep = 724.3` 은 동률이 아니라 **−84.6** 이다.

## ⛔ 검출력 문제 — 계획했던 2시드 설계로는 판정이 안 된다

시드 단독 sd 가 **22.0 (f2024) · 28.9 (f2023)** 이다. 예측 #3 이 건 효과 크기가
"±20 이내" 인데 그건 이 설계에서 **검출 불가능한 크기**다.
[[preregister-power-not-just-thresholds]] — 규율을 다 지켜놓고 동전 던지기를 한다.

→ 판정 전에 **이 학습기의** k 시드 평균 산포를 직접 잰다 (`--seedspread`).
   MLP 의 22 를 트랜스포머에 그대로 쓰면 안 된다 [[noise-floor-is-learner-specific]].
   그 sd 가 나온 뒤에 설계(팔 수 × 시드 수)를 다시 정한다.

| 팔 | 핸디캡 | 보너스 | 필요값 |
| --- | ---: | ---: | ---: |

in-sample 격자조차 이 팔을 안 쓴다.

⚠️ 시드를 늘리면 단독은 오르지만 **상관도 같이 오른다**(평균낼수록 모든 것과 닮는다).
   병목이 핸디캡이 아니라 보너스라 그 방향으로는 안 풀린다.

## ★ 소득 — "다른 아키텍처 = 다른 오차" 는 자동이 아니다

트랜스포머는 MLP 와 구조가 완전히 다른데 **오차는 더 닮았다**(corr .922, LGBM 상대로는
MLP 보다 더 높다). 같은 피처 · 같은 인코딩 · 같은 손실을 쓰면 함수족 차이가 오차
다양성으로 자동 전환되지 않는다. MLP 가 얻은 탈상관(.90~.93)은 "MLP 라서"가 아니라
다른 데서 온 것일 수 있다 — 그렇다면 그 출처를 찾는 것이 새 아키텍처를 더 시도하는
것보다 값이 크다.

## ⛔ 정정 1 의 가설이 틀렸다 — `d` 는 **단조 증가**다

정정 1 은 *"수치 71개를 71×64 로 펴는 것은 §7.26(PLE 73→381 기각) 방향이고 12배 더
극단적이라 −68 핸디캡의 유력 용의자"* 라고 적었다. 실측은 반대다: 32 < 64 < 128.
**MLP 에서 나온 PLE 결과가 트랜스포머로 전이되지 않았다.**
[[noise-floor-is-learner-specific]] · [[literature-transfers-by-regime-not-by-method]]

⚠️ 단 `d128` 을 그대로 읽으면 안 된다 — 시드 sd 36.3 은 기준(9.5)의 **4배**다.
   차이의 SE ≈ 21.7 → **+24.7 은 1.1σ**. 평균은 높고 훨씬 불안정하다
   (용량이 늘어 분산도 같이 커진 전형적 모습).

`ffn_mult` 는 2.0 이 국소 최적이다 (1.0 −15.2 · 4.0 −5.8). 이 축은 이미 맞게 잡혀 있었다.

## ★★ corr 이 크기와 무관하다 — 그래서 크기로는 값 경로가 안 열린다

| | corr(LGBM) | 핸디캡 | 보너스 |
| --- | ---: | ---: | ---: |
| MLP 슬롯 | .935 | — | ≈ +40 |
| ftt d32 | .931 | −95.9 | −5.6 |
| ftt d64 | .938 | −69.8 | −0.1 |
| ftt **d128** | .941 | −45.2 | **+5.4** (필요 22.6) |
| ftt `sem8` | .945 | −55.2 | +3.8 (필요 27.6) |

파라미터를 58k → 299k 로 5배 흔들었는데 **corr 은 .93~.945 에 붙어 있다.** 단독만
오르고 오차의 방향은 안 변한다. 크기를 더 키워도 핸디캡만 줄고 보너스가 안 따라온다.

### 크기 노브는 같은 함수를 더 잘 맞출 뿐, 다른 함수를 만들지 않는다

크기 변형끼리의 상관: `d32`↔`d32ffn1` **.999** · `ffn1`↔`ffn4` .995 · `d64`↔`ffn4` .997.
그런데 **`sem8` 은 다른 트랜스포머 변형들과 .961~.982 로 눈에 띄게 낮다** —
**어텐션 마스크가 크기 노브 전부보다 함수를 더 많이 바꾼다.**
헤드 분할이 실재하는 구조적 변경이라는 증거고, 결과 ③(그룹 비교)이 재는 것이 그것이다.

노이즈: 전 팔 풀링 단독 sd **22.1**(f2024) · 17.9(f2023)
→ 3시드평균 sd 12.8 / 10.3 → **팔 간 차이 SE 18.0 / 14.6**

## 판정 — 통과한 것이 없다

| scheme | ① vs `full` | ② vs 위약 |
| --- | --- | --- |
| `sem8` | +14.6 (0.8σ) · +3.2 (0.2σ) — 부호 O | +18.9 (1.0σ) · **−7.4** — 부호 **X** |
| `sem8ov` | +17.4 (1.0σ) · +8.8 (0.6σ) — 부호 O | +21.8 (1.2σ) · **−1.8** — 부호 **X** |
| `subj3` | +2.8 · −0.9 — 부호 **X** | −3.1 · −7.7 — 둘 다 음수 |

**전부 1.2σ 미만이고, 관문 ②가 fold 간 부호 반전으로 깨진다.**
fold2023 에서는 **위약(`shuf@sem8` 629.0)이 전 팔 중 1위**다 — 진짜 그룹 셋을 다 이겼다.
[[nonsense-bucket-is-the-null-for-subgroup-tuning]] 의 패턴 그대로다.

## ⛔ 검출력을 또 낙관했다

`full` 한 팔에서 잰 시드 sd 12.3 으로 "3시드면 SE 9.8" 이라 했는데, **전 팔 풀링은 22.1**
이다 (`subj3` 는 혼자 36.2). 실제 SE 는 **18.0** 이었다. +15 규모를 2σ 로 잡으려면
팔당 17시드가 필요하다 — 이 설계로는 처음부터 불가능했다.
→ [[noise-floor-is-learner-specific]] 는 **같은 학습기 안의 팔 사이에도** 적용된다.
   한 팔에서 잰 노이즈를 다른 팔에 쓰면 안 된다.

## ★ 상관이 말하는 것 — 내가 앞서 읽은 것과 반대다

결과 ② 에서 *"마스크가 크기 노브 전부보다 함수를 더 많이 바꾼다"* 고 적었는데,
전 팔을 놓고 보면 **위약이 가장 다른 모델**이다:

    shuf@sem8 는 다른 모든 팔과 corr .965~.980 으로 최저
    sem8/sem8ov/subj3 는 full 과 .981~.995

즉 함수를 갈라놓는 것은 **의미 있는 그룹이 아니라 제약의 무작위성**이다.
의미 그룹은 `full` 이 쓰던 어텐션 경로를 대체로 보존하므로 `full` 과 가깝게 남는다.

# 정정 3 — 앵커에서 **보조 헤드(aux)** 를 빠뜨렸다 (사용자 지적 "로짓 보정", 2026-08-30)

`train.py` 와 `foldcache.compute` 는 둘 다 MLP 를 `y_aux=aux, aux=MLP_AUX_LAMBDA`
(λ=1.0, 축 `("middle","reverse")`) 로 학습한다. 내 `run_anchor` 는 안 넘겼다.

```
                    aux OFF (내가 쓰던 앵커)   aux ON (정정)
fold2024 MLP 슬롯          808.9         →      841.0    +32.1
fold2023 MLP 슬롯          629.0         →      630.1     +1.1
배포형 블렌드 기준         829.1         →      849.9
```

fold 비대칭이 크다 — 보조 축이 "몰림·반대" 인데 fold2023 은 그 라벨 정의가 바뀐
구간(§3.1a)이라 신호가 약한 것과 일관된다.

| | 이전 보고 | 정정 |
| --- | ---: | ---: |
| 최고 트랜스포머(`d128`) 핸디캡 | −45.2 | **−77.3** |
| 필요 보너스 | 22.6 | **38.7** |
| 실측 보너스 | +5.4 | +5.4 |
| `sem8ov` 단독 vs 앵커 (f2024) | −52 | **−84** |

**결론은 안 바뀌고 강해진다.** corr 도 그대로다 — `mlp_slot`↔LGBM .941 인데
트랜스포머 전 팔이 .930~.945 로 같은 대역이다.

## 확인해둔 것 — 다른 로짓 보정은 안 빠뜨렸다

| 보정 | 상태 |
| --- | --- |
| prior shift (`shift_to_prior`) | ✅ `mlp.score()` 가 전 팔·앵커에 동일 적용 |
| `init_score` / `offset` | ✅ **MLP 배포 경로엔 원래 없다.** `mlp.train_mlp(offset=)` 은 §7.114 실험(`mlpinit.py`)만 쓰고 `train.py`·`foldcache` 는 안 넘긴다. 내 LGBM 앵커도 `foldcache` 와 같이 init_score 없이 돌려 층이 일치 |
| δ_F 로짓 오프셋 | β=0 비활성 (config §7.69) |
| **보조 헤드 aux** | ❌ **빠뜨렸다 → 위에서 정정** |

## → 다음 실험이 여기서 나온다

결과 ① 의 결론은 *"같은 피처·같은 인코딩·**같은 손실**을 쓰면 구조를 바꿔도 오차가
안 갈린다"* 였다. 그런데 방금 **손실을 바꾸는 것이 +32.1** 임을 확인했고, 내
트랜스포머는 그 손실을 안 쓴다. 즉 지금 잰 corr .938 은 **손실이 다른 두 모델**의
상관이다.

트랜스포머에 aux 를 달았을 때:
- corr 이 그대로면 → 결론이 훨씬 강해진다 (손실을 바꿔도 안 갈린다)
- corr 이 떨어지면 → **결론이 뒤집힌다.** 값 경로가 아키텍처가 아니라 **손실**에
  있었다는 뜻이고, 그건 챔피언 작업에 바로 쓰인다 (새 아키텍처를 더 시도하는 것보다
  보조 타깃 축을 늘리는 쪽이 값이 크다)

# 정정 4 — **δ 축(`logit_adjust`)을 fold 층이 아예 안 만든다** (사용자 지적, 2026-08-30)

사용자가 "로짓 보정" 을 세 번 물었고, 세 번째에야 내가 제대로 봤다.

## 무엇이 빠져 있었나

배포 `predict.py:347` 은 행 단위 사후 로짓 보정을 더한다:

```
z = z + CTX_BETA_MULT * logit_adjust(test_df, art)      # Σ β·δ, 4갈래 축
p = sigmoid(z + logit_delta)                            # logit_delta = −0.04497
```

배포 artifacts 의 살아 있는 축:

    ctx  hand         β = 1.875      ctx  count4       β = 1.25
    asof gap_success  β = 0.03       asof gap_bsuccess β = 0.03
    mix  없음                        gt   δ = −0.0 (비활성)

그런데 **이 축들은 `fit_artifacts` 가 아니라 `train.py` 가 만든다** (ctxfit /
asofdelta / mixent, line 446·457·460). `foldcache.fold_data` 는 `fit_artifacts`
만 부르므로 fold 층 `art` 에는 축이 없고 `logit_adjust` 가 **전 팔에 정확히 0** 이었다.
→ "내가 δ 를 안 걸었다" 가 아니라 **"fold 층에 걸 대상이 없었다"** 이고, 그 자체가
   층 격차다. [[run-diagnostics-on-the-deployed-layer]]

## fold 층에서 축을 직접 fit 해서 재측정 (재학습 0회, `ftt_delta2.py`)

⚠️ **학습 시즌으로만 fit 했다** (train.py 는 전체 df 로 하지만 그건 홀드아웃 없는
   최종 빌드라서다). β 는 배포 스택 위에서 정해진 값이라 단독 팔에 그대로 더하는
   것은 근사다 — **순위 변화의 방향만** 읽고 절대값은 읽지 않는다.

δ: 비영행 100% · sd 0.051 · 범위 [−0.277, +0.365]
적중률 hand .801 · count4 .801 · gap_success .801 · gap_bsuccess .907

| 팔 | δ 없이 | δ 적용 | **δ 이득** |
| --- | ---: | ---: | ---: |
| `ftt_sem8` | 753.7 | 830.0 | **+76.3** ← 최소 |
| `ftt_sem8ov` | 756.6 | 833.3 | +76.7 |
| `mlp_slot` | 841.0 | 918.1 | +77.0 |
| `lgb12` | 811.6 | 895.5 | +83.9 |
| `ftt_subj3` | 741.9 | 828.6 | +86.7 |
| `ftt_shuf_sem8` | 734.8 | 823.0 | +88.2 |
| `ftt_full` | 739.1 | 831.1 | +92.0 |
| `ftt_full_d128` | 763.8 | 854.4 | +90.6 |
| `ftt_full_d32ffn1` | 711.3 | 814.0 | **+102.7** ← 최대 |

## ★★ 이중 계상이 실측됐다 — 그리고 결과 ③ 의 판정이 바뀐다

δ 를 **가장 적게 버는 팔이 정확히 `hand`·`count` 전용 헤드를 가진 분할 팔**이다.
이미 잡은 구조라 δ 가 더 줄 게 없다. 약한 팔일수록(`d32` +102.7) 많이 번다.

```
                δ 없이    δ 적용
ftt_sem8        753.7     830.0
ftt_full        739.1     831.1
sem8 − full     +14.6      −1.1      ← **부호 반전**
sem8ov − full   +17.5      +2.2      ← 거의 소멸
```

**헤드 분할의 이득으로 보였던 것이 배포가 이미 적용하는 δ 보정을 대신하고 있었다.**
δ 가 자리에 있으면 분할이 더 주는 것이 없다. [[count-what-a-new-correction-double-subtracts]]

결과 ③ 은 *"① 은 통과, ② 에서 부호 반전"* 이라고 적었는데, **δ 를 걸면 ① 도 무너진다.**

| 블렌드 `0.25·lgb + 0.75·X` | δ 없이 | δ 적용 |
| --- | ---: | ---: |

| ftt 최고 (`d128`) | 793.1 | 882.0 |
| 격차 | −56.8 | **−46.6** |

## 내가 틀렸던 말

*"δ 는 전 팔에 동일하게 더해지니 비교엔 무해하다"* — **틀렸다.** 같은 벡터를 더해도
팔마다 **잔차 겹침이 달라** 순위가 바뀐다. 가산 보정이라고 순위 보존이 아니다.
